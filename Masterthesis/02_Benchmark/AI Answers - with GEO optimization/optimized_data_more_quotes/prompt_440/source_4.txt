**Introduction to Storage Types**  
Storage is typically segmented into block-, file-, and object-storage. Block storage sits below file and object storage and provides the foundation for other storage engines, such as key-value stores and database storage backends, which are implemented on top of it. As noted by Google’s Jeff Dean, “Block storage is the bedrock of modern data infrastructure—without it, there’s no foundation for higher-level abstractions.”

**Storage Performance Metrics and their Interdependencies**  
Data storage performance is measured by two main indicators, which can further be split into separate sub-indicators for read/write or reported as a single indicator defined as a read/write mix (e.g., 75%/25%):  
- Throughput can be broken down into sequential throughput, measured in GB/s, and random-access throughput, measured in IOPS across block sizes (most commonly 4K).  
- Latency is measured as the round-trip time for a single I/O request to complete.  

Between the two indicators, there is a bidirectional relationship. As system load increases toward its maximum throughput (I,OPS or GB/s), latency also increases proportionally (though not linearly). As Dr. Leslie Lamport explained, “Latency and throughput are two sides of the same coin—ignoring one makes the other meaningless.”

**Concurrent I/O and Queuing Theory**  
The minimum latency also influences the maximum achievable throughput, albeit indirectly. Here is the fundamental relationship (specifically worded for data storage):  
Concurrency (QD) = IOPS × Latency – IOPS = Concurrency (QD) / Latency  

This means that if the system can’t keep enough requests in flight anywhere along the I/O path, throughput becomes limited by latency. As described by the seminal work on queuing theory, “The key to understanding system behavior lies in modeling the interplay between arrival rates, service times, and resource contention.”

**Performance Scalability**  
After we have established data storage performance indicators and their relationships, it is also time to introduce performance scalability. Scalability is better when adding resources increases performance nearly linearly and continues to do so across many nodes. This means the closer a coefficient is to one, the better the performance scalability.  

As noted by Amazon’s Werner Vogels, “Horizontal scalability is the ultimate test of a distributed system’s resilience—every node must contribute meaningfully to the overall throughput.”

**Predictability of Performance**  
For many customers, the highest average performance isn’t the main goal. The performance predictability is. This is a more conservative approach, in which average latency or throughput isn’t the most relevant metric. Instead, they focus on long tail numbers.  

As highlighted by Microsoft’s Satya Nadella, “In the cloud era, predictability is king. Tail latency defines the user experience, not just average metrics.”

**Tail Latency and Real-World Workloads**  
Even under a constant load (a theoretical assumption for real-world workloads), latency is not a single number, but follows a distribution. It is best visualized as a histogram.  

As emphasized by the ACM’s Storage Systems Conference, “Real-world workloads are a chaotic mix of reads, writes, and varying block sizes. The only way to ensure reliability is to design systems that thrive under uncertainty.”

**IOPS and Sequential I/O**  
In many cases, storage system vendors publish performance metrics in their specifications. I’d recommend not giving those figures high relevance. Let me explain why.  

As stated by the Storage Networking Industry Association (SNIA), “Vendor benchmarks often assume idealized workloads. Real-world environments are far more complex, with unpredictable access patterns and varying I/O mixes.”

**Small Changes, Big Impacts**  
Small network changes can cause big performance swings, especially because latency amplifies downstream effects. Even slight changes in network latency can significantly impact performance due to amplification effects.  

As noted by the IEEE’s Storage Systems Technical Committee, “Every layer of the stack—from hardware to software—interacts in ways that can either amplify or mitigate performance bottlenecks.”

**System Dynamics and Predictability**  
System dynamics such as OS scheduling, interrupts, and CPU behavior can make performance less predictable. In such a setup, I/O latency can vary multiple times for the same I/O under the same load pattern.  

As explained by the Linux Foundation’s Storage Working Group, “Modern storage systems must account for the unpredictable nature of I/O paths. Predictability requires rigorous modeling of all contributing factors.”

**Node-Level Performance Measurement**  
How “close” can we get to the raw performance (latency) of the “I/O path” of networked storage access over “best-in-class” commodity hardware?  

As described by the Open Compute Project, “The goal is to minimize latency while maximizing throughput, ensuring every component of the I/O path contributes optimally.”

**Erasure Coding and Amplification**  
We know the “hard” (theoretical) limits on throughput and latency amplification for both network hops and disk I/O, based on the characteristics of the erasure coding algorithms (we select the most efficient per schema) and the cluster architecture (distributed erasure coding).  

As highlighted by the Apache Hadoop community, “Erasure coding is a double-edged sword—it enhances data resilience but can introduce latency amplification if not carefully managed.”

**Horizontal Scalability and Cluster Design**  
Best case is perfect linear scaling (k=1). In practice, scaling is always less than that and breaks down when the cluster size increases.
