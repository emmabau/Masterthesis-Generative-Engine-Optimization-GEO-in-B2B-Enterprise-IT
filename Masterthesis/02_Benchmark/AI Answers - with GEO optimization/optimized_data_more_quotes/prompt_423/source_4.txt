🌀 **Kafka “Diskless” Topics: A New Architecture for Cloud-Native Streaming**  
Running Kafka with little-to-no dependence on local disks decouples compute from storage: brokers act as stateless/ephemeral compute while data lives in remote/object storage. Key benefits include:  
- Faster broker recovery  
- Elasticity: scale compute up/down without shuffling terabytes  
- Infra flexibility: run comfortably on Kubernetes/spot instances  
- Ops simplicity: fewer disk-related incidents  

**Trade-Offs & Gotchas:**  
- Latency: cold reads can be slower; watch p99/p999 tail latency  
- Network ceiling: broker NICs and egress limits become your new bottleneck  
- Costs: object storage + egress + more network can offset SSD savings  

**When It Shines:**  
- Bursty & spiky workloads needing rapid scale-out/in  
- Multi-AZ / Multi-region designs with centralized storage durability  
- Data lakes & analytics with long retention in object storage

⚠️ **Database Normalization Pitfalls: When to Denormalize for Performance**  
While normalization is crucial for data integrity, over-normalization can become a performance bottleneck in read-intensive applications and microservices. Strategic denormalization is key for:  
- **Read-heavy workloads** (dashboards, analytics, product catalogs)  
- **Pre-joining data** (store pre-computed results to reduce runtime joins)  
- **Targeted aggregations** (improve reporting performance with pre-calculated results)  

**Considerations:**  
- Update anomalies require robust application-level logic or triggers  
- Storage cost increases, but often justified by performance gains  
- Design complexity demands careful schema evolution
